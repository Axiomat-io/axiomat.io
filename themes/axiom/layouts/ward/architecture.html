System architecture

How Ward is put together.

One Svelte client, one FastAPI app, one scheduler job, and a Postgres database with row-level security scoping every table to a workspace. Everything else — the model, the payment processor, the tools an agent can call — is an external service Ward talks to, not something it owns.

ward — Azure Container App

Seven modules, one FastAPI process.

🌐 server.py

The HTTP surface — agent CRUD, chat, run triggers, billing endpoints, admin.

🧠 Agent Runtime

agent.py, dynamic.py — runs the tool loop against Azure OpenAI, resolves an agent's power level to a backing model at build time.

💳 Metering & Billing

metering.py, tiers.py, billing.py — weighted daily run quota per workspace, Stripe Checkout + webhook sync to tier.

🔌 MCP Manager

mcp.py, mcp_oauth.py — discovers, authorizes, and calls user-connected MCP servers. No first-party integrations.

🛡️ Policy / Audit / Provenance

policy.py, audit.py, provenance.py — deny lists, approval gates, run-level audit trail, source attribution on retrieved data.

🔔 Notifications & Webhooks

notifications.py, webhooks.py — outbound alerts and inbound triggers for agent runs.

🪪 Auth

auth.py — session handling in front of Auth0's hosted login.

Scheduled execution

Cron runs its own copy of the code — not a call into the API.

ward-scheduler is a distinct Azure Container App Job. On each tick, main.py --tick reads due agents straight from Postgres and imports agent.py/dynamic.py directly in its own process — the same code path the API uses for "Run Now," but a separate process, not a network call into the running API container.

Data & storage

Isolation enforced by the database, not app code.

🗄️ ward-pg

Azure Postgres Flexible Server. Every table carries row-level security keyed to workspace_id — no query can read across workspaces, even by mistake. This is also where the highest-sensitivity data lives: mcp_oauth stores encrypted third-party OAuth tokens for every MCP server a user connects.

📦 Artifact storage

Azure Blob (or local filesystem in dev) behind a pluggable ArtifactStore — agent-produced files, chat attachments.

External services

The model, the processor, the integrations — all outside the app.

🤖 Azure OpenAI — AI Foundry

Three deployments back the three power levels: gpt-5.6-luna (Normal), gpt-5.6-terra (High), gpt-5.6-sol (Max) — swappable per-catalog, never hardcoded on an agent.

💳 Stripe

Checkout for self-serve upgrades; signature-verified webhooks sync subscription state back to a workspace's tier.

🔑 Auth0

Hosted SPA login — Ward never stores a password.

🧩 User-connected MCP servers

Slack, Gmail, GitHub, Notion, and anything else a user adds — the integration surface is MCP, not a Ward-built connector.

Being straight with you

What this diagram doesn't show yet.

This is a snapshot of what's actually deployed today, not an aspirational one — so here's what's deliberately left off, and why:

🔓 No Key Vault

Secrets (Stripe, Auth0, Azure OpenAI, the DB connection string) are Azure Container App secrets, injected as env vars — not Key Vault + managed identity.

🌐 No VNet / private endpoint

ward-pg is reachable over its public endpoint, gated by an IP allowlist — not a private network path.

📈 No dedicated observability

Tracing hooks exist in the code (tracing.py) but no APM/exporter is wired up yet — logs land in the Container App environment's default Log Analytics workspace.

📦 Shared container registry

axiomatioacr also serves other Axiomat projects — it isn't Ward-dedicated infrastructure.
